# Block 24 — Agent Security: Sandboxing, Guardrails, and Data Isolation

## The Security Model for Agents

Traditional software security assumes: code is deterministic, inputs are validated, outputs are predictable.

Agent security must handle: non-deterministic behavior, tool calls generated by an LLM (not by code you wrote), and outputs that can contain arbitrary content.

**Core principle:** The agent is untrusted. It runs in a sandbox. Every action it takes passes through a policy layer. Every output is scanned before it leaves the system.

## Layer 1: Tool Execution Sandboxing

### The Problem

When an agent generates code or tool calls, that code runs on your infrastructure. A manipulated agent could:
- Execute arbitrary commands (`os.system("rm -rf /")`)
- Read sensitive files (`open("/etc/shadow")`)
- Make unauthorized network requests
- Consume unlimited resources

### Sandboxing Approaches

| Approach | Isolation Level | Overhead | Use Case |
|----------|----------------|----------|----------|
| **MicroVMs (Firecracker)** | Strongest — dedicated kernel | ~5MB memory, 125-200ms boot | Code execution (untrusted) |
| **gVisor** | Strong — user-space syscall interception | Lower than VMs | Kubernetes agent pods |
| **Hardened containers** | Moderate — namespaces + cgroups + seccomp | Minimal | Trusted tool execution |
| **Process-level** | Minimal — subprocess with resource limits | Negligible | Simple tool calls (no code exec) |

**For your crash triage agent** (tool calls, not code execution): hardened containers are sufficient. Tools are pre-defined functions, not arbitrary code.

**For code-generation agents** (Codex, Cursor, Devin-like): MicroVMs or gVisor are necessary. The generated code is untrusted.

### Implementing Tool Sandboxing

```python
class SandboxedToolExecutor:
    def __init__(self, allowed_tools, resource_limits):
        self.allowed_tools = set(allowed_tools)
        self.limits = resource_limits  # {timeout_s, max_memory_mb, max_output_bytes}
    
    def execute(self, tool_name, args, context):
        # Policy check: is this tool allowed?
        if tool_name not in self.allowed_tools:
            return {"error": f"Tool '{tool_name}' is not permitted"}
        
        # Scope check: are the arguments within bounds?
        if not self.validate_scope(tool_name, args, context):
            return {"error": "Arguments violate scope policy"}
        
        # Rate limit check
        if self.rate_limiter.is_exceeded(tool_name):
            return {"error": "Rate limit exceeded for this tool"}
        
        # Execute with resource limits
        try:
            result = run_with_limits(
                self.tools[tool_name],
                args,
                timeout=self.limits["timeout_s"],
                max_memory=self.limits["max_memory_mb"]
            )
        except TimeoutError:
            result = {"error": "Execution timed out"}
        except MemoryError:
            result = {"error": "Memory limit exceeded"}
        
        # Output size limit
        if len(json.dumps(result)) > self.limits["max_output_bytes"]:
            result = truncate(result, self.limits["max_output_bytes"])
        
        return result
```

## Layer 2: Guardrails (Input/Output Policies)

### Input Guardrails

Applied to the user's request and to tool results before they reach the agent:

```python
class InputGuardrails:
    def check(self, content, source):
        results = []
        
        # Injection detection
        if self.injection_detector.scan(content):
            results.append(GuardrailViolation("injection_detected", source))
        
        # PII detection (in case sensitive data reaches the agent)
        pii_findings = self.pii_detector.scan(content)
        if pii_findings:
            content = self.pii_detector.redact(content)
            results.append(GuardrailWarning("pii_redacted", pii_findings))
        
        # Content policy (toxic, harmful, off-topic)
        if not self.content_policy.is_allowed(content):
            results.append(GuardrailViolation("content_policy", source))
        
        return content, results
```

### Output Guardrails

Applied to the agent's response before it reaches the user or any external system:

```python
class OutputGuardrails:
    def check(self, agent_output, context):
        results = []
        
        # Secret detection
        secrets = self.secret_scanner.scan(agent_output)
        if secrets:
            results.append(GuardrailViolation("secrets_in_output", secrets))
            agent_output = self.secret_scanner.redact(agent_output)
        
        # System prompt leakage
        if self.prompt_leak_detector.check(agent_output, context.system_prompt):
            results.append(GuardrailViolation("prompt_leakage"))
        
        # Format validation (output matches expected schema)
        if not self.schema_validator.validate(agent_output, context.expected_schema):
            results.append(GuardrailWarning("schema_mismatch"))
        
        # Confidence check
        if agent_output.confidence < context.min_confidence:
            results.append(GuardrailWarning("low_confidence"))
        
        return agent_output, results
```

### Deny-by-Default Policy

The Guardplane pattern (2026): agents can do nothing by default. Every capability must be explicitly granted:

```yaml
agent: crash-triage
policies:
  tools:
    allowed:
      - query_opensearch:
          indices: ["c3server-*"]
          operations: ["read"]
      - query_prometheus:
          operations: ["query", "query_range"]
      - create_jira_comment:
          projects: ["PTOP"]
          requires_approval: true
    denied:
      - "*"  # everything else denied
  
  network:
    allowed:
      - "opensearch.internal:9200"
      - "prometheus.internal:9090"
      - "api.anthropic.com:443"
    denied:
      - "*"
  
  filesystem:
    allowed:
      - "/tmp/agent-workspace/*": "rw"
    denied:
      - "*"
  
  resource_limits:
    max_tokens_per_investigation: 100000
    max_tool_calls_per_investigation: 20
    max_duration_seconds: 600
    max_cost_dollars: 5.00
```

## Layer 3: Data Isolation Between Agents

In multi-agent systems, agents should not have unrestricted access to each other's data.

### Isolation Boundaries

```
┌─────────────────────┐    ┌─────────────────────┐
│ Log Analyst Agent    │    │ Metrics Analyst Agent│
│                      │    │                      │
│ Tools: OpenSearch    │    │ Tools: Prometheus    │
│ Context: isolated    │    │ Context: isolated    │
│ Memory: private      │    │ Memory: private      │
│                      │    │                      │
│ Can read: shared_state│   │ Can read: shared_state│
│ Can write: own_results│   │ Can write: own_results│
└──────────┬──────────┘    └──────────┬──────────┘
           │                          │
           └────────┬─────────────────┘
                    ↓
            ┌──────────────┐
            │ Shared State  │
            │ (controlled)  │
            │               │
            │ ACL per key   │
            │ Audit logged  │
            └──────────────┘
```

### Implementation

```python
class IsolatedAgentContext:
    def __init__(self, agent_id, permissions):
        self.agent_id = agent_id
        self.private_memory = {}  # only this agent can access
        self.permissions = permissions
    
    def write_shared(self, shared_state, key, value):
        if not self.permissions.can_write(key):
            raise PermissionError(f"Agent {self.agent_id} cannot write to {key}")
        shared_state.write(self.agent_id, key, value)
    
    def read_shared(self, shared_state, key):
        if not self.permissions.can_read(key):
            raise PermissionError(f"Agent {self.agent_id} cannot read {key}")
        return shared_state.read(key)
```

**Why isolation matters:** If Agent A is compromised via prompt injection, it can only affect its own context and the shared state keys it has write access to. It cannot directly manipulate Agent B's context or tools.

## Layer 4: Audit Trail

Every agent action is logged to a tamper-evident audit trail:

```python
@dataclass
class AuditEntry:
    timestamp: str
    agent_id: str
    action_type: str      # "tool_call", "tool_result", "llm_call", "guardrail_violation"
    tool_name: str | None
    arguments: dict | None
    result_hash: str       # hash of the result (not the result itself, for large outputs)
    guardrail_results: list
    context_tokens: int
    
    def to_jsonl(self):
        return json.dumps(asdict(self)) + "\n"
```

**Append-only log:** Entries are written sequentially and cannot be modified. If a security event occurs, the audit trail provides a complete replay of what happened.

## Key Takeaways

> "The agent is untrusted code. It runs in a sandbox, every action passes through a policy layer, and every output is scanned. This is the same security model as a web browser — the JavaScript (agent) is sandboxed, and the browser (runtime) enforces policies."

> "Deny-by-default is the only safe starting point. List what the agent CAN do, not what it CAN'T. Every unlisted capability is denied. This prevents the unknown unknowns."

## Build — Agent Security Middleware

Build a complete security middleware that sits between an agent and its tools.

**Requirements:**
1. **Policy engine**: load YAML policy, evaluate each tool call against it
2. **Scope enforcement**: validate tool arguments against allowed values (correct cluster, time range, etc.)
3. **Rate limiter**: per-tool and per-agent rate limits
4. **Input scanner**: scan tool results for injection patterns before returning to agent
5. **Output scanner**: scan agent output for secrets, PII, prompt leakage
6. **Resource limiter**: track total tokens, cost, tool calls per session. Enforce limits.
7. **Audit logger**: append-only JSONL log of all actions
8. **Approval gate**: for write operations (e.g., create_jira_comment), pause and wait for human approval

**Test:** Run an agent through the middleware. Attempt: (a) calling a disallowed tool, (b) exceeding rate limit, (c) injecting via tool result, (d) producing output with a fake API key. Verify all are caught.

**What you'll learn:** How little overhead a security middleware adds (~5-10ms per tool call), how deny-by-default policies prevent entire classes of attacks, how audit trails enable post-incident forensics.

## Design — Zero-Trust Agent Platform

Design a platform where agents run in a zero-trust environment — no agent is trusted by default, every action is verified.

**Requirements:**
- Each agent runs in an isolated container with minimal privileges
- Tools are exposed as microservices behind an API gateway. Agents authenticate to tools with scoped tokens.
- Every tool call is logged, rate-limited, and policy-checked at the gateway
- Agents cannot communicate directly — all communication goes through a mediated message bus
- Human approval required for any action with real-world side effects
- Real-time monitoring: tool call anomaly detection, cost tracking, injection detection

**Design decisions:**
- How do you issue and rotate scoped tokens for each agent?
- How do you handle the latency overhead of the API gateway? (Acceptable for tool calls, but what about high-frequency operations?)
- How do you handle the cold start problem? (Agent needs to authenticate, load policy, initialize context before it can do anything)
- How do you test the security model? (Red team exercises? Automated penetration testing?)
- How does this scale to 100 agents? 1000?
